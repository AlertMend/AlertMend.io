git config --global http.sslBackend schannel: What It Does and How to Fix Errors

The short answer

Use schannel only when your Git build supports Windows certificate trust.

git config --global http.sslBackend schannel tells Git to use the Windows Secure Channel TLS backend, commonly through Git for Windows and libcurl.

It helps when Windows already trusts your company or proxy CA. It does not fix Linux, WSL, Docker, or Git builds that only support openssl or gnutls.

What http.sslBackend = schannel means

Git uses libcurl for HTTPS operations such as clone, fetch, and push. The http.sslBackend setting chooses which TLS backend libcurl should use when that Git build supports runtime backend selection. On Windows, schannel means Secure Channel, the Windows TLS stack that can use the Windows certificate store.

TL;DR: On Git for Windows, schannel can be the clean fix for corporate certificates already trusted by Windows. On unsupported builds, it is not a fix — it becomes the error.

Should you set schannel?

Yes

Use it on Git for Windows when Windows already trusts the company root CA and Git HTTPS commands do not.

No

Do not use it on Linux, WSL, Docker, most CI images, or any Git build reporting supported backends as only openssl or gnutls.

Maybe

Be careful when http.sslCAInfo is set. With schannel, Git normally avoids letting that bundle replace Windows trust unless configured otherwise.

Pick your failure

Same setting. Different real fix.

The command is useful only in the right environment. Select the symptom you actually see.

$ observed result git config --global http.sslBackend schannel git ls-remote https://github.com/org/repo.git # Git uses Windows certificate trust
Interpretation

Use schannel when Git for Windows should trust the Windows certificate store.

This is the common corporate Windows fix: the company root CA is already trusted by Windows, and Git should use that same trust store instead of a separate OpenSSL CA bundle.

git config --global http.sslBackend schannel
git config --global http.sslVerify true
git ls-remote https://github.com/org/repo.git

Fix: Good fit for Git for Windows when the Windows Trusted Root store already contains the CA that signs your proxy or repository certificate.

Safe fix checklist

Follow this order so you fix the trust path instead of hiding the error.

1

Find the source

Run git config --show-origin --get-all http.sslBackend. If the bad setting came from global config, unset it globally; if it came from system config, fix it through your managed Git image or endpoint policy.

2

Match the OS

Use schannel for supported Git for Windows builds. Use OS trust or http.sslCAInfo for OpenSSL/GnuTLS environments.

3

Keep verification on

Keep http.sslVerify=true. If Git cannot verify the server, add the correct CA or choose the correct backend.

4

Verify with Git

Run git ls-remote <url> in the same terminal, runner, WSL distro, or container that failed.

SymptomBest fixWhy it works
Windows Git cannot trust corporate proxy git config --global http.sslBackend schannel Git uses the same Windows certificate trust that your browser and endpoint policy use.
Unsupported backend: gnutls git config --global --unset http.sslBackend Removes a Windows-only backend from a Git build that cannot use it.
Unsupported backend: openssl Unset schannel, then set http.sslCAInfo to a PEM CA bundle if needed. OpenSSL-style Git expects a file or OS CA path, not the Windows Schannel backend.
Revocation check error Fix CRL/OCSP access; only then consider http.schannelCheckRevoke=false with approval. Revocation failures are not the same as missing-issuer failures.

What not to do

Anti-pattern

git config --global http.sslVerify false

That may silence the error, but it also disables Git certificate verification. The safer fix is to use the backend your Git supports and make the right CA trusted by that environment.
