What does no healthy upstream mean?

No healthy upstream means the reverse proxy or load balancer received your request but has zero backend servers passing health checks. The proxy itself is running, every upstream host is down, failing probes, or ejected by the service mesh. Envoy documents this state as no_healthy_upstream: the router rejected the request because it found no healthy upstream. Envoy reference ↗

You typically see HTTP 503 Service Unavailable with a plain-text body such as no healthy upstreamno healthy backendsor upstream server responded with a 503 error. Upstream servers are the application instances behind the proxy. When every upstream fails health checks, users get a total outage at the edge even if container processes are still running.

CodeNameProxy behaviorMeaning
502Bad GatewayProxy reached a backendBackend returned invalid or corrupt response
503Service UnavailableProxy has no backend to tryZero healthy upstreams; pool empty
504Gateway TimeoutProxy reached a backendBackend did not respond within timeout

HTTP 503 Service Unavailable explained

HTTP 503 is a 5xx server error indicating the server is temporarily unable to handle the request. With no healthy upstreamthe condition is usually fixable once backends recover or probes pass. Unlike misconfiguration errors that need code changes, 503 often clears when health checks succeed again.

ALERTMEND FIELD NOTE 01“Running” is process state; “Ready” is traffic eligibility.

During this incident, the Ready condition and EndpointSlice are more useful than restart count. A pod can run perfectly while Kubernetes correctly refuses to send it traffic.

Reproduce empty upstreams safely

This isolated lab creates two nginx pods with an intentionally broken readiness path. The containers run, but Kubernetes marks them NotReady and does not publish them as ready Service endpoints. That reproduces the cluster state behind many no healthy upstream incidents without touching an existing application.

Safety: Run this only in a disposable cluster or an approved non-production context. The manifest uses its own upstream-lab namespace, and the final command deletes that namespace.

Download the reproducible lab manifest ↓Plain YAML · isolated namespace · cleanup included

yaml
✗ Problem
apiVersion: v1
kind: Namespace
metadata:
  name: upstream-lab
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-api
  namespace: upstream-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: demo-api
  template:
    metadata:
      labels:
        app: demo-api
    spec:
      containers:
      - name: nginx
        image: nginx:1.27-alpine
        ports:
        - containerPort: 80
        readinessProbe:
          httpGet:
            path: /intentionally-broken
            port: 80
          periodSeconds: 3
          failureThreshold: 1
---
apiVersion: v1
kind: Service
metadata:
  name: demo-api
  namespace: upstream-lab
spec:
  selector:
    app: demo-api
  ports:
  - port: 80
    targetPort: 80
shell 
# Safety: use a disposable cluster or non-production context.
kubectl config current-context

# Apply the intentionally broken workload from the manifest above.
kubectl apply -f upstream-lab.yaml
kubectl wait --for=jsonpath='{.status.phase}'=Running pod \
  -l app=demo-api -n upstream-lab --timeout=90s

# Observe: pods run, readiness fails, and no ready endpoint is published.
kubectl get pods -n upstream-lab
kubectl get endpointslice -n upstream-lab \
  -l kubernetes.io/service-name=demo-api -o wide

# Repair the readiness path and watch endpoints become ready.
kubectl patch deployment demo-api -n upstream-lab --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/"}]'
kubectl rollout status deployment/demo-api -n upstream-lab
kubectl get endpointslice -n upstream-lab \
  -l kubernetes.io/service-name=demo-api -o wide

# Clean up the isolated lab.
kubectl delete namespace upstream-lab

Error 503 no healthy backends

Error 503 no healthy backends is interchangeable with no healthy upstream on many proxies. Envoy, Istio ingressgateway, Fastly/Varnish VCL, and several cloud load balancers use "backends" in the message. The diagnosis is identical for all: find why every backend failed health checks, check backend health, not the proxy config.

Message variants by platform (same root cause, different wording):

  • 503 backend is unhealthyCDNs and some PaaS edge layers
  • health checks failed with these codes: [503]AWS target group health checks
  • no healthy targetsApplication Load Balancer (ALB)
  • 503 backend fetch failedVarnish cache miss / backend fetch
  • no live upstreamsnginx when every server in upstream {} is marked down
  • unhealthy upstreamgeneric reverse-proxy wording

nginx: upstream blocks and passive health checks

On bare metal or VM nginx, the same symptom appears when every server in the upstream block is marked down. nginx no live upstreams and nginx 503 service temporarily unavailable often mean zero upstream servers passed passive health checks. Use max_fails and fail_timeout with sane timeouts:

shell 
upstream backend {
    least_conn;
    server backend1:8080 max_fails=3 fail_timeout=30s;
    server backend2:8080 max_fails=3 fail_timeout=30s;
    keepalive 32;
}

server {
    location / {
        proxy_pass http://backend;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
        proxy_next_upstream error timeout http_502 http_503;
    }
}

Check error logs: grep -i upstream /var/log/nginx/error.log. Test backends directly: curl -v http://backend-ip:8080/health.

Envoy 503 no healthy upstream and upstream connect errors

Envoy returns a local 503 when a cluster has healthy_hosts: 0. Look for response flag UH (no healthy upstream) in access logs. In Istio, check DestinationRule outlier detection and VirtualService subsets.

shell 
# Envoy / Istio: common log lines
# response flag UH = no healthy upstream
# upstream connect error or disconnect/reset before headers

kubectl logs -n istio-system deploy/istio-ingressgateway | grep -iE 'no healthy upstream|UH|upstream connect'

# Check cluster health in admin (debug port-forward)
# curl localhost:15000/clusters | grep -A5 <service-name>

upstream connect error or disconnect/reset before headers

This Envoy error means the proxy could not establish a TCP connection to any upstream host. UH (no healthy upstream) and UF (upstream connection failure) often co-occur: the cluster may list hosts, but every connection attempt fails before HTTP headers arrive.

Common reset reason variants in access logs and debug output:

  • connection timeoutupstream did not accept TCP within the connect timeout
  • connection failureTCP refused, no route, or immediate RST from the host
  • connection terminationpeer closed the socket during handshake or before headers
  • overflowcircuit breaker or pending-request limit blocked new connections
  • remote connection failurenetwork path failure between Envoy and pod IP

HAProxy and AWS ALB: no healthy IP / no healthy targets

Error 503 no healthy IP available for the backend is HAProxy-specific. 503 no healthy targets is common on AWS ALB when every target fails health checks. Verify backend server state, security groups, and that health check paths return 200.

Kong: failure to get a peer from the ring-balancer

Kong returns this when the ring-balancer has no upstream node to route to, every target is unhealthy, DNS resolution failed, or the upstream has zero registered targets. Check target health via the Kong admin API before editing routes or plugins.

Three mistakes that make 503 worse

These are the reflex moves that feel productive but extend outages. Each fails for a mechanical reason, and has a better first step.

1. Restarting the ingress controller or nginx

Kubernetes populates Service endpoints from Ready pods via kube-proxy, not from the ingress controller process. Restarting nginx or ingress-nginx clears connection pools but does not change which pod IPs are in the endpoints list. If every pod fails readiness, you get the same 503 on a fresh controller. Instead: fix Ready pods first, confirm kubectl get endpoints shows IPs, then restart ingress only if endpoints are populated but the proxy still returns 503 (stale config cache).

2. Deleting pods to "force refresh"

Deleting pods during a broken rollout triggers the Deployment to create replacements that hit the same failing readiness probe. You go from "pods Running but not Ready" to "zero pods while new ones start." During scale events this can cascade across nodes. Instead: read probe Events with kubectl describe podfix the probe path or startup timing, then rollout restart once the probe config is corrected.

3. Editing proxy upstream config when endpoints are empty

When ENDPOINTS is <none>the proxy is already pointing at a Service with no backends. Changing upstream {} blocks, proxy_passor VirtualService routes does not create Ready pods, it only changes where an empty pool points. Instead: restore at least one healthy backend, verify endpoints repopulate, then tune proxy timeouts or health checks if needed.

Restarting the proxy rarely fixes empty endpoints. Fix backends first. Restart ingress only after confirming endpoints are populated but proxy still returns 503 (stale config cache).
