You do not need to automate everything. Start with the recurring work that is the same every time: freeing a full disk, renewing a certificate, restarting a stuck worker, sweeping idle cloud spend. Not what to automate. What to automate first.

The mistake is trying to automate everything at once, or automating the interesting thing instead of the frequent thing. The tasks that pay back first are the ones that are both routine and time-consuming: you do them constantly, they follow the same steps every time, and they need almost no judgment. Plot your work on two axes, how often you do it and how long each run takes, and the priority order falls out on its own.

The 12 recipes

Each one is a real piece of daily ops work, written as a runbook you can lift. The config is illustrative; the real runbook is visual, versioned, and fanned out across your fleet.

Keep it running

Alert-triggered fixes for the things that break during the day.
1

Free up a disk before it pages you

ON ALERT

By hand today: You get paged for a full volume, SSH in, hunt for the biggest files, delete, and restart whatever fell over.

trigger: disk_used(/) > 85%            # or a nightly cron
steps:
  - run     du -sh /var/log/* | sort -h | tail
  - s3      archive /var/log/*.gz  ->  s3://logs-archive/$host/
  - approve channel=slack                # the next step deletes
  - run     truncate -s 0 /var/log/*.log ; docker system prune -f
  - notify  slack: "$host reclaimed <gb>G, back to <used>%"
~25 min per incident, and no 2am page Approval before it deletes at scale
2

Restart a stuck service or worker

ON ALERT

By hand today: You notice a health check gone red or a queue backing up, SSH in, restart the process, and watch it recover.

trigger: healthcheck(app) fails x3      # ~90s window
steps:
  - run     journalctl -u app -n 50       # capture the why first
  - run     systemctl restart app
  - check   healthcheck(app) == ok
  - branch  if still failing:
      - notify slack @oncall "$host: restart did not recover app"
~15 min per occurrence Escalates to on-call if the restart does not recover it
3

Recover a CrashLoopBackOff pod

ON ALERT

By hand today: You see restart counts climbing, run describe and logs, then delete the pod or roll back the deploy by hand.

trigger: pod.restarts > 5 in 10m
steps:
  - run     kubectl describe pod $pod ; kubectl logs $pod --previous --tail=80
  - branch  if it looks like a bad deploy:
      - run    kubectl rollout undo deploy/$deploy
    else:
      - run    kubectl delete pod $pod           # reschedule clean
  - notify  slack: pod, node, action taken
~20 min per incident Rolls back only the affected deployment
4

Absorb a queue backlog

ON ALERT

By hand today: Traffic spikes, the queue grows, and you manually scale workers up, then remember to scale them back down later.

trigger: queue_depth(orders) > 5000 for 5m
steps:
  - run     kubectl scale deploy/worker --replicas=12
  - wait    until queue_depth < 500          # max 20m
  - run     kubectl scale deploy/worker --replicas=3
  - notify  slack: peak depth, drain time, replicas used
~30 min, and a missed SLA avoided Scales back to baseline automatically

Prevent the 3am page

Scheduled hygiene that stops the incident before it happens.
5

Renew TLS certificates before they expire

SCHEDULED

By hand today: You track expiry dates in a spreadsheet, renew by hand, reload the web server, and hope you did not miss one.

trigger: cron 0 6 * * *                 # daily
steps:
  - check   for host in endpoints: days_to_expiry(host)
  - branch  if days_to_expiry < 14:
      - run    certbot renew            # or re-issue via ACM
      - run    nginx -t && systemctl reload nginx
      - check  new cert served, expiry > 60d
  - notify  slack: renewed hosts + next-to-expire watchlist
~1 hour a month, and the outage a lapsed cert causes
6

Verify backups actually restore

SCHEDULED

By hand today: You trust the backup job exited zero, and find out it was broken only when you actually need to restore.

trigger: cron 0 3 * * 0                 # weekly
steps:
  - run     restore latest dump  ->  scratch database
  - check   row counts and checksums within tolerance
  - run     drop scratch database
  - branch  if check failed: page @oncall   # silent backup = real risk
  - notify  slack: PASS/FAIL, restore time, rows verified
a silent backup failure, caught before you need it Pages on-call if the test restore fails
7

Run nightly database maintenance

SCHEDULED

By hand today: You occasionally kill a long query and run VACUUM by hand, usually after the database has already slowed down.

trigger: cron 0 2 * * *                 # nightly, low traffic
steps:
  - run     terminate queries where state=active and runtime > 30m
  - run     VACUUM (ANALYZE)
  - run     REINDEX INDEX CONCURRENTLY <bloated_index>
  - notify  slack: dead tuples reclaimed, longest query killed
~20 min a day, and the slow-query incident it prevents
8

Rotate and ship logs off the box

SCHEDULED

By hand today: Logs fill the disk, you rotate and gzip by hand, then copy them somewhere before the volume fills again.

trigger: cron 30 1 * * *
steps:
  - run     gzip $(find /var/log -name '*.log' -mtime +1)
  - s3      sync /var/log/*.gz  ->  s3://logs/$host/   # then remove shipped
  - run     find /var/log -name '*.gz' -mtime +7 -delete
  - check   disk_used(/) after, report reclaimed
a recurring disk-full page, gone

Stop paying for idle

Scheduled sweeps that hand money back to FinOps.
9

Power down idle dev and staging overnight

SCHEDULED

By hand today: Non-production runs all night because nobody remembers to stop it, and the monthly bill shows it.

trigger: cron 0 20 * * 1-5  (stop)  /  0 8 * * 1-5  (start)
steps:
  - check   instances tag:env=nonprod, state=running
  - run     stop them              # the morning job starts them back
  - notify  slack: stopped N instances, saved ~<X> per night
~65% of non-prod compute cost
10

Delete orphaned volumes and old snapshots

SCHEDULED

By hand today: Unattached volumes and stale snapshots pile up until a quarterly cost review that rarely actually happens.

trigger: cron 0 4 * * 1                 # weekly
steps:
  - check   volumes status=available + snapshots older than 30d
  - approve channel=slack                # deletion needs a human
  - run     delete approved volumes and snapshots
  - notify  slack: reclaimed ~<X>/mo, deleted IDs (audited)
real monthly spend, and hours of cleanup Approval before anything is deleted
11

Prune Docker on CI runners and hosts

SCHEDULED

By hand today: A runner disk fills with dead images and build cache, builds fail with no space left, and someone SSHes in.

trigger: disk_used(/) > 80% on ci-runners   # or nightly
steps:
  - run     docker system prune -af --volumes --filter "until=168h"
  - run     docker builder prune -af
  - notify  slack: "$host reclaimed <gb>G of image and build cache"
broken builds from a full runner, prevented

See it without logging in

Scheduled visibility, pushed to where the team already is.
12

Send a morning fleet-health digest

SCHEDULED

By hand today: You open three dashboards every morning to piece together whether anything actually needs your attention today.

trigger: cron 0 8 * * 1-5
steps:
  - gather  hosts up/down, pods crashlooping, certs < 30d,
            last backup status, idle-resource spend
  - format  one card, red items first
  - notify  slack #ops   (+ WhatsApp to the on-call lead, optional)
~15 min a day per person, and earlier awareness

Two of these, on the day they mattered

The recipes look small on paper. Here is what they are worth when it counts.

E-commerce · peak traffic · recipe 1

The 2am disk that almost took down checkout

It is 2:11am on the busiest sales night of the year. A noisy deploy triples log volume and /var on the checkout tier hits 98%. Orders start failing with 500s at the worst possible moment.

Without automation

The page fires, on-call wakes up, connects to the right host, finds the runaway log, and truncates it. Fifteen minutes, most of it just getting to a terminal, and every minute is lost orders at peak.

With the runbook

At 85% the runbook had already archived the logs to S3, truncated, pruned Docker, and posted "checkout-3 reclaimed 22G, back to 41%" to Slack. The 500s never started and nobody woke up.

MTTR from ~15 minutes to ~40 seconds, and zero lost checkout minutes
SaaS · reliability · recipe 5

The certificate nobody was watching

A wildcard cert on the API gateway is set to expire Sunday at 03:00. It lives in three places and one spreadsheet, and the one that matters is not on the spreadsheet. No one is looking.

Without automation

Monday morning every mobile client fails TLS, support lights up, and the team burns the first hour of the week finding which cert lapsed instead of shipping.

With the runbook

Every morning a scheduled runbook checked days-to-expiry across all endpoints. It saw 12 days left, re-issued, reloaded nginx, verified the new cert was being served, and posted the next-to-expire watchlist. The Monday outage simply never happened.

A full TLS outage avoided, and about an hour a month of manual tracking gone

How AlertMend runs all twelve

Every recipe above follows the same shape: a trigger, a check, an action, an optional approval on the destructive step, and a recorded result. AlertMend runs the host-level ones agentlessly over SSH, and reaches Kubernetes, cloud APIs, databases, and messaging through connectors, so there is no per-server agent to install or maintain. A step can fan out across every host or pod that matches, so one runbook covers three servers today and three hundred next year without a rewrite.

The parts that make it safe to run against production are built in. Destructive steps pause for a Slack, Microsoft Teams, or Email approval, permissions are scoped with RBAC, and every host touched, command run, and file removed is recorded, so a scheduled sweep is auditable rather than a black box. That is the difference between a cron script you are afraid to trust and automation you are happy to leave running. For the reactive side of the same engine, recovering a crashlooping service or a stuck deploy the moment an alert fires, see cross-stack incident automation, and for the host layer specifically, VM monitoring and auto-remediation.

The payoff: a single "clean the disk over 85%" recipe covers your whole backend fleet in one scheduled pass, with nobody watching and a human signing off only before it deletes. Multiply that by the eleven others and you are handing your team back a meaningful slice of every week.
