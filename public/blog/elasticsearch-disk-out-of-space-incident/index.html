What triggers the read-only block

Elasticsearch uses three disk watermarks. At the low watermark (default 85%) it stops allocating most new shards to the node. At the high watermark (90%) it tries to relocate shards away. At the flood-stage watermark (95%) it applies a read-only-allow-delete block to every index with a shard on the affected node. The block permits deleting an entire index to recover space; document writes and deletes remain blocked.

This is a safety mechanism, not a bug. The durable recovery sequence is: create headroom, monitor relocation, and verify the block is removed. In current releases Elasticsearch normally removes the block automatically after disk usage falls below the high watermark; clear it manually only if it remains.

How to diagnose it

1

Find the full node

Run GET _cat/allocation?v to see disk.percentdisk.usedand disk.avail for every node. The one above 95% owns the incident.

2

Confirm the block

Run GET _all/_settings/index.blocks.read_only_allow_delete. A value of true confirms the flood-stage block was applied.

3

See what is using space

Run GET _cat/indices?v&s=store.size:desc to find the largest indices, and check for old or duplicate indices safe to delete.

4

Check for custom watermarks

Run GET _cluster/settings?include_defaults=true&flat_settings=true and inspect the cluster.routing.allocation.disk.watermark.* values in case they were changed.

Common causes and fixes

Unbounded index growth

Logs or metrics indices grow forever with no rollover or retention.

Fix: Adopt an ILM policy that rolls over by size or age and deletes old indices.

Undersized data volume

The PersistentVolume is simply too small for the workload.

Fix: Expand the PVC (if the StorageClass allows) or add data nodes to spread shards.

Oversized shards or too many replicas

Large shards and extra replicas multiply on-disk footprint.

Fix: Right-size shards (tens of GB each) and review replica count for the index.

Merge and translog overhead

Segment merges and translog need free headroom to operate.

Fix: Keep 15 to 25% free; do not run data nodes near the watermarks by design.

One hot node

Uneven allocation fills a single node while others have room.

Fix: Check allocation balance; the high watermark should relocate shards, so investigate why it did not.

Fix it step by step

Recover in order: create headroom, verify you are under the watermark, then clear the block. Never clear the block first.

# 1. Free space: delete a confirmed-retired index (or expand capacity)
DELETE /logs-2026.05

# 2. Confirm the node falls below the high watermark
GET _cat/allocation?v
GET _cluster/health

# 3. Current versions normally remove the block automatically.
# If it remains after disk is healthy, clear it explicitly:
PUT */_settings?expand_wildcards=all
{ "index.blocks.read_only_allow_delete": null }

# 4. Confirm writes and relocation recover
GET _cat/recovery?v&active_only=true
GET _cluster/health?wait_for_status=yellow&timeout=120s

Do not permanently raise watermarks to hide a capacity problem. Elastic recommends the defaults for most clusters; add capacity, reduce retained data, or correct shard sizing instead.

Prevent it from recurring

The durable fix is retention plus headroom. Use Index Lifecycle Management to roll over indices by size or age and delete them on schedule, so no index grows without bound.

PUT _ilm/policy/logs-policy
{
  "policy": {
    "phases": {
      "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "7d" } } },
      "delete": { "min_age": "30d", "actions": { "delete": {} } }
    }
  }
}

Then size data volumes so nodes sit comfortably under the low watermark during normal operation, and alert on disk.percent crossing 80% so you act before the flood stage ever triggers.
