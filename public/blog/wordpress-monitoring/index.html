What keeps WordPress up

WordPress powers a huge share of the web, and most production sites are more than PHP and a database: a web server, PHP-FPM workers, MySQL, an object cache, wp-cron, and often WooCommerce all have to work together. A page can render from a full-page cache or CDN while the parts that matter, login, wp-admin, and checkout, are quietly broken.

That is why monitoring WordPress means watching the whole path, not just that the homepage returns 200. The signal that a store is losing money is a failed checkout or a stalled wp-cron, and neither shows up in a simple uptime ping.

What to monitor in WordPress

A green web server does not prove customers can log in or buy. Watch the whole path from browser to database.

Site and checkout URL

journey

Poll the homepage plus a logged-in or add-to-cart path from outside; alert on non-200 or slow responses.

PHP-FPM workers

process

Track busy vs max_children and request queueing; exhausted workers cause 502 and 504 errors.

MySQL health

database

Watch slow queries, connections, and a bloated wp_options autoload, the usual root of a slow WordPress.

Object cache

cache

Redis or Memcached hit rate; a down or cold cache pushes all load onto MySQL and slows every page.

wp-cron

jobs

Confirm scheduled events run; a stalled wp-cron silently breaks publishing, emails, and WooCommerce actions.

Disk and PHP memory

capacity

Uploads filling disk, or memory_limit hit, produce failed uploads and the white screen of death.

Copy-paste health checks

Run these from the host or a monitor to separate a full outage from a slow or partial failure.

# Site answering (follow redirects, show status)
curl -sSI -L https://your-site.com/ | head -n1

# PHP-FPM pool status (enable pm.status_path in the pool config)
curl -s http://127.0.0.1/status?full

# MySQL responsiveness and slow queries
mysqladmin -u root -p status
mysql -e "SHOW FULL PROCESSLIST;" | grep -i query

# wp-cron and scheduled events (WP-CLI)
wp cron event list --fields=hook,next_run_relative

# Redis object cache reachable
redis-cli ping

Monitor WordPress with Prometheus and Grafana

WordPress has no single official exporter, so the standard Prometheus and Grafana stack combines four: blackbox_exporter for the URL and checkout path, mysqld_exporter for MySQL, a PHP-FPM exporter for worker saturation, and node_exporter for host CPU, memory, and disk.

# Probe the site and a checkout path from outside via blackbox_exporter
curl -s "http://localhost:9115/probe?module=http_2xx&target=https://your-site.com/checkout/"

# php-fpm exporter reads the pool status page (enable pm.status_path)
# mysqld_exporter reads SHOW GLOBAL STATUS; node_exporter covers the host

Key metrics to scrape and graph in Grafana:

  • blackbox: probe_success and probe_http_duration_seconds for site and checkout
  • php-fpm: active vs total processes and the listen queue
  • mysql: threads_running, slow_queries, and connections
  • node: disk, inode, memory, and CPU

Common failures and safe fixes

White screen of death

A blank page with no error usually means a PHP fatal or the memory_limit being hit, often from a plugin, theme, or update.

Fix: Enable WP_DEBUG or read the PHP error log, raise memory_limit if legitimate, and disable the offending plugin. Keep a governed rollback for the last update.

502 or 504 errors

The web server has no healthy PHP-FPM worker: the pool is down, crash-looping, or all children are busy under load.

Fix: Restart or scale the PHP-FPM pool, raise pm.max_children within memory budget, and cache more aggressively to cut backend load.

Site is slow

Slowness is usually MySQL: slow queries, a huge autoloaded wp_options, or a missing or cold object cache pushing load onto the database.

Fix: Add or warm a Redis object cache, trim autoloaded options, index or kill slow queries, and add full-page caching.

wp-cron not running

Scheduled posts, emails, and WooCommerce jobs stop when wp-cron is disabled or never triggered, common on low-traffic sites.

Fix: Disable pseudo-cron and run wp-cron from a real system cron every 1 to 5 minutes, and alert when events fall behind.

WooCommerce checkout failing

Orders stall in pending or fail at payment when the gateway callback, MySQL, or PHP workers are degraded.

Fix: Test the full checkout path from outside, watch the payment gateway webhook, and confirm workers and MySQL have headroom at peak.

WordPress monitoring FAQ

WordPress slowness is usually MySQL (slow queries or a bloated autoloaded wp_options) or a missing or cold object cache pushing all load onto the database, sometimes with too few PHP-FPM workers. Add a Redis object cache, trim autoloaded options, add full-page caching, and index or kill slow queries.
A blank page with no error is usually a PHP fatal or the memory_limit being hit, often from a plugin, theme, or update. Enable WP_DEBUG or read the PHP error log, raise memory_limit if the usage is legitimate, and disable the offending plugin.
A 502 means the web server has no healthy PHP-FPM worker: the pool is down, crash-looping, or every child is busy under load. Restart or scale PHP-FPM, raise pm.max_children within your memory budget, and cache more aggressively to cut backend load.
By default wp-cron only fires when someone visits a page, so low-traffic sites miss scheduled posts, emails, and WooCommerce jobs. Disable the pseudo-cron with DISABLE_WP_CRON and run wp-cron from a real system cron every 1 to 5 minutes, and check wp cron event list.
Checkout stalls when the payment gateway callback, MySQL, or PHP workers are degraded, so orders sit in pending. Test the full checkout path from outside, watch the gateway webhook, and confirm workers and MySQL have headroom at peak.
Set pm.max_children to roughly the RAM available for PHP divided by the average PHP process size. Too few workers cause 502 and 504 errors under load, too many exhaust memory, so watch the pool status page for queueing.
Poll the homepage plus a logged-in or add-to-cart path from outside on an interval, and separately watch PHP-FPM, MySQL, and disk. A cached homepage alone hides login, admin, and checkout failures.
The gateway webhook that confirms payment did not reach the site, or wp-cron did not process the status change. Verify the gateway callback URL is reachable and that wp-cron is running on a real schedule.
MySQL is down, out of connections, or the credentials or host in wp-config.php are wrong. Check the MySQL service, its max_connections, and the database settings, then confirm the site can reach the database host.
