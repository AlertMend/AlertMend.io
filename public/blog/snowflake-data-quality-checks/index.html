How do I check data quality in Snowflake?

Snowflake makes it easy to load data and hard to notice when that data is wrong. A late load, a duplicated key, or a column that silently fills with nulls rarely fails a query. It produces a wrong number in a report instead.

The practical approach has three layers. Start with SQL you can run today for the checks that catch the most incidents. Reach for Snowflake data metric functions where a simple scheduled per-table metric is enough. Then move to continuous monitoring when you need thresholds per table, noise control, and a link from a failure to the job that caused it and the reports it affects.

  • Freshness: did the data arrive on time?
  • Volume: did we get roughly the usual number of rows?
  • Completeness: are mandatory fields filled?
  • Uniqueness: are keys really unique?
  • Validity and referential integrity: are values in range and do foreign keys resolve?

Freshness, volume, completeness, uniqueness and validity in Snowflake SQL

These five checks cover most day-to-day data quality incidents. Each one is a plain query you can run in a Snowflake worksheet against your own tables. The sample schema names below (BANKING, FINANCE, KYC) are placeholders, swap in your own.

Freshness: most tables carry a load timestamp. Compare the latest one with when you expected the load, using DATEDIFF for the gap. Alert when minutes_late passes the table's agreed arrival time. Freshness is usually the first check to add, because a late table breaks every report built on it.

Volume: a feed that delivers half its normal rows often loads without any error. Compare today's count with recent history. COUNT_IF and IFF make this compact, letting you pivot today versus the trailing average in one pass. A fixed band (for example plus or minus 30 percent) is a good start, and history-based anomaly checks reduce noise later.

Completeness: check that mandatory fields are filled. COUNT_IF counts the offending rows directly, and NULLIF guards the divide so an empty table does not raise a division error. Set the allowed rate per column. Regulatory fields often allow zero.

Uniqueness: a retried load or a join that fanned out can duplicate a key while every query keeps working. Group by the key and keep the groups with more than one row. Returning sample keys with a LIMIT makes the alert actionable instead of just a count.

Validity and referential integrity: validity checks that values sit in an allowed set or numeric range. Referential integrity checks that foreign keys resolve, using a LEFT JOIN and filtering for the rows with no match.

In practice: A duplicated key that no query rejected

At 06:12 the nightly_load job retried a step and loaded a batch of BANKING.CUSTOMER_ACCOUNTS twice.

Every query still ran. The uniqueness of account_id quietly dropped to 98.7 percent, and three Power BI reports began double counting balances.

A one-line GROUP BY check would have caught it at load time, before the 9am meeting saw the wrong number.

The most expensive data quality failures do not throw errors. They pass every query and surface as a wrong figure in a report, so the check has to run on a schedule, not just when someone remembers to look.

Snowflake data metric functions: what they do and do not give you

Snowflake also offers data metric functions (DMFs) that attach to a table or view and run on a schedule you set. System DMFs in the SNOWFLAKE.CORE schema cover common metrics such as null counts, duplicate counts, row counts and freshness, and results land in an event table you can query. They are a good fit for simple, per-table metrics you want Snowflake to compute for you.

Two limits to plan around

Per Snowflake documentation, custom (user-defined) data metric functions require Enterprise Edition or higher, and running DMFs consumes serverless compute credits billed against your account. Confirm your edition and cost expectations before you standardize on them. System DMFs cover the basics, but not everything you may want to assert.

What DMFs do not give you is the context around a failure. They tell you a metric crossed a line. They do not tell you which pipeline run caused it, which Power BI reports read the affected table, or which policy clause the check exists to enforce. They also do not manage alert noise, approvals, or an audit trail of who changed a check and why.

  • Good for: scheduled null, duplicate, row-count and freshness metrics on a single table.
  • Not built for: cause and impact, noise control, approvals, versioning, or policy traceability.
  • Edition gate: custom DMFs need Enterprise Edition, and all DMFs use serverless credits.

From queries to continuous monitoring

Writing the SQL is the easy part. Running it well, on every table, every day, without drowning your team in false alerts, is the work. Ad hoc queries answer a question once. Continuous monitoring answers it on a schedule and tells you what to do next.

  1. Schedule each check near the data
    Run a check just after the table it watches lands, not on a fixed nightly batch that fires hours after the incident.
  2. Tune thresholds per table
    A 30 percent volume swing is normal for one feed and an incident for another. History-based checks should wait for enough history instead of guessing on day one.
  3. Control noise
    Cooldowns, maintenance windows and flapping detection stop one broken table from paging you twenty times.
  4. Connect cause and impact
    Link a failed check to the pipeline run that produced the data and the reports that read the table, so the on-call engineer sees the whole picture in the alert.
  5. Keep an audit trail
    Record which rule enforces which policy clause, who approved it, and what changed, so an auditor gets proof in minutes rather than spreadsheets.
