What SIGSEGV and exit code 139 mean

A modern CPU and operating system give every process its own virtual address space, enforced by the Memory Management Unit. When a process reads or writes an address that is not mapped, or that it lacks permission for, the hardware raises a fault and the kernel delivers SIGSEGV (signal 11). The default action is to terminate the process, which is why you see Segmentation fault (core dumped). This is a safety mechanism: the alternative is silent memory corruption.

TL;DR: exit code 139 is not random. It always means signal 11 (SIGSEGV). The task is to find the exact line that touched bad memory, not to add a retry.

When a shell, container runtime, or orchestrator reports a numeric exit code for a process killed by a signal, it uses 128 + signal number. It helps to know the neighbours, because a crash loop can be any of them and each has a different fix.

Exit codeSignalMeaningFirst move
139 SIGSEGV (11) Segmentation fault: invalid memory access. Core dump + gdb backtrace, or an AddressSanitizer build.
137 SIGKILL (9) Killed, most often OOMKilled at a memory limit. Check memory limit and usage, not the code first.
134 SIGABRT (6) abort(), failed assert, or glibc heap corruption check. Read the abort message, then the backtrace.
135 SIGBUS (7) Bad address alignment or a truncated mmap'd file. Check alignment and memory-mapped file sizes.
136 SIGFPE (8) Arithmetic error, typically integer divide by zero. Guard the divisor and integer overflow paths.

Read the one line the kernel already gave you

Before you reach for a debugger, the kernel usually logged a single line to the ring buffer. Reading it well answers "null or wild pointer, read or write, stack or heap" in seconds.

$ dmesg | tail -1 app[12903]: segfault at 0 ip 000055f6b2c0 sp 00007ffd1290 error 6 in app[556000+2000]
FieldWhat an experienced eye reads from it
at 0The faulting address. at 0 is a textbook null dereference. A small value like at 18 is a null struct pointer plus a field offset, so ptr->field where ptr is null. A giant address is a wild or corrupted pointer.
ipInstruction pointer: where the CPU was executing. Turn it into a source line without gdb: addr2line -e ./app -f 0x55f6b2c0 (build with -g).
spStack pointer. If the faulting address sits at or just below sp, suspect a stack overflow from deep recursion, not a bad data pointer.
error 6A bitmask. Bit 0: 0 = page not present, 1 = protection. Bit 1: 0 = read, 1 = write. Bit 2: 1 = user mode. So error 4 is a user read of unmapped memory, error 6 is a user write to unmapped memory, and error 7 is a write to read-only memory such as a string literal.

$ python app.py Segmentation fault (core dumped) # pure Python rarely segfaults on its own
Interpretation

A managed runtime segfault points at native code.

In Python or Node a real SIGSEGV almost always comes from a C extension, an FFI or ctypes misuse, or recursion deep enough to overflow the C stack. Turn on the native traceback.

python -X faulthandler app.py # prints the C traceback on crash # or inside the code: import faulthandler; faulthandler.enable()

Fix: update or rebuild the offending native module, correct the FFI call signature, or lower recursion depth. Reproduce against the extension in isolation.

$ docker run myimage Segmentation fault $ docker inspect --format '{{.State.ExitCode}}' $(docker ps -lq) 139
Interpretation

The process inside the container hit SIGSEGV.

Besides an ordinary bug, a common container cause is an image built for a different CPU architecture running under emulation, where native code segfaults. Check the platform and reproduce with a debug build.

docker image inspect myimage --format '{{.Os}}/{{.Architecture}}' uname -m # host architecture docker run --rm -it --entrypoint sh myimage # then run under gdb

Fix: build the image for the node's platform (--platform linux/amd64 or linux/arm64), or debug the crashing binary with a core dump inside the container.

Fix: roll back the deploy that introduced the crash, then debug the binary with a core dump or an AddressSanitizer build before re-releasing.

The five causes behind most segfaults

Almost every SIGSEGV traces back to one of these memory mistakes. Each has a small reproducer and a direct fix.

1

Null or uninitialized pointer

Reading or writing through a pointer that is NULL or was never set. Fix: initialize pointers and check before dereferencing.

2

Out-of-bounds access

Indexing past the end of an array or buffer, including an off-by-one. Fix: validate lengths and use bounds-checked APIs.

3

Use-after-free

Using a pointer after free(), or a double free. Fix: set pointers to NULL after freeing and own lifetimes clearly.

4

Stack overflow

Infinite or very deep recursion, or a huge stack array. Fix: add a base case, bound the depth, or heap-allocate large buffers.

5

Write to read-only memory

Modifying a string literal or a const mapping. Fix: copy into a writable buffer before mutating.

Why the same bug crashes sometimes and not others

A segfault is undefined behavior, and undefined behavior is allowed to look like it works. A use-after-free often reads fine because the freed block has not been reused yet. An out-of-bounds read returns garbage instead of faulting when the neighbouring page happens to be mapped. This is why "works on my machine" and "only crashes in production" are real engineering facts, not excuses.

1

Debug vs release

The optimizer reorders code, inlines frames, and reuses stack slots, so an uninitialized read that was harmless in a debug build faults in release.

2

ASLR moves things

Address space layout randomization changes addresses each run, so a wild pointer lands on a mapped page one time and an unmapped one the next.

3

Heap layout and timing

Under light load a freed allocation is still intact; under real traffic it gets reused, and only then does a use-after-free corrupt live data.

4

Allocator differences

A different glibc, jemalloc, or musl changes sizing and poisoning, so a bug that hides on your laptop surfaces in the container image.

Make "sometimes" into "always": run with MALLOC_PERTURB_=42 and MALLOC_CHECK_=3, or rebuild with AddressSanitizer, which turns an intermittent crash into a deterministic report at the exact faulting line.

How to debug a SIGSEGV, in order

A segfault is one of the most debuggable failures there is, because the crash captures the exact machine state. Work from the core dump inward.

1

Capture a core dump

Run ulimit -c unlimited, reproduce, and check /proc/sys/kernel/core_pattern. On systemd, use coredumpctl list and coredumpctl gdb.

2

Read the backtrace

gdb ./app core, then bt full for the call stack and locals, and frame N to inspect the faulting line. Build with -g for symbols.

3

Rebuild with AddressSanitizer

gcc -g -fsanitize=address app.c -o app. ASan reports use-after-free, heap and stack overflow with the allocation and access site.

4

Or run under valgrind

valgrind --leak-check=full --track-origins=yes ./app catches invalid reads and writes without a rebuild, at the cost of speed.

$ gdb -q ./app core Program terminated with signal SIGSEGV, Segmentation fault. #0 0x000055f in parse_row (r=0x0) at parser.c:88 88 return r->columns[0]; (gdb) bt #0 parse_row (r=0x0) at parser.c:88 #1 load_file (path=0x7ffd...) at parser.c:142 #2 main (argc=2, argv=0x7ffd...) at main.c:30 (gdb) print r $1 = (Row *) 0x0
Read it like an expert: the crash is at frame #0, but the bug is one frame up. r is 0x0, so parse_row was handed a null Row by load_file, which returned NULL for a missing file that nobody checked. You fix the caller, not the line that happened to fault.
Pick the right tool: gdb on a core shows WHERE it crashed, not always WHY. AddressSanitizer (a rebuild, roughly 2x slower) catches use-after-free and overflows at the exact site and is the fastest route to root cause. Valgrind needs no rebuild but runs 20 to 50x slower and shifts timing enough to hide race-related crashes. Reach for ASan first when you can rebuild, and valgrind when you cannot.

What a segfault looks like in each language

SIGSEGV means the same thing to the kernel everywhere, but each runtime dresses it up differently and each has a preferred first tool. If you are not writing C, the segfault is almost always in native code underneath you.

Exit code 139 in Docker and Kubernetes

In a cluster you often see the symptom before the signal: a container in CrashLoopBackOff rather than the words "segmentation fault". The most important first step is to separate a segfault (139) from an OOMKilled container (137), because they lead to opposite fixes.

139 vs 137: Exit Code: 139 with Reason: Error is a segfault, so debug the binary. Exit Code: 137 with Reason: OOMKilled means it hit the memory limit, so adjust limits or usage. Same crash loop, different root cause.
1

Read previous logs

kubectl logs POD --previous holds the output from the crashed container instance, often with the last thing it did before the fault.

2

Confirm the exit code

kubectl describe pod POD and check Last State. Exit Code 139 confirms SIGSEGV rather than OOM or a config error.

3

Correlate the deploy

Did the crash start after a rollout or an image bump? A recent change is the fastest lead. Roll back to stop the loop while you debug.

4

Get a core out of the pod

Set a writable core_pattern path on the node or an ephemeral debug container, then pull the core to analyze the binary with symbols.

Getting a core out of production and distroless containers

The most common reason a production segfault stays unsolved is that no core was ever captured. Containers make this worse: the kernel writes the core using the host's core_pattern, not anything you set inside the container, so ulimit -c unlimited in the entrypoint is necessary but not sufficient.

1

core_pattern is host-wide

Check cat /proc/sys/kernel/core_pattern on the node. On systemd hosts it pipes to systemd-coredump, so the core is in coredumpctl list and opens with coredumpctl gdb.

2

Distroless has no shell

You cannot run gdb inside a distroless image. Attach an ephemeral debug container that shares the process namespace: kubectl debug -it POD --image=busybox --target=app, or copy the core off the node.

3

Snapshot a live process

If a process is hung rather than crashed, gcore PID writes a core without killing it, so you can inspect state and let it keep running.

4

Keep your symbols

Production binaries are usually stripped, so bt shows ??. Keep the unstripped binary or a .debug file, or wire up debuginfod, so the backtrace has names.

Treat cores as sensitive: a core dump is a snapshot of process memory and can contain tokens, keys, and customer data. Restrict who can read cores, scrub them before sharing, and think twice before uploading one, especially under compliance.

SIGSEGV FAQ

SIGSEGV is signal 11, a segmentation fault. The operating system sends it to a process that tried to read or write a memory address it is not allowed to touch, such as a null pointer or memory outside an allocation. The kernel terminates the process to protect the rest of the system, usually printing "Segmentation fault (core dumped)".
Exit code 139 is how a shell or container reports a process killed by SIGSEGV. The convention is 128 plus the signal number, and SIGSEGV is signal 11, so 128 + 11 = 139. If you see exit code 139 in Docker, Kubernetes, or CI, the program segfaulted.
The common causes are dereferencing a null or uninitialized pointer, reading or writing past the end of an array or buffer, using memory after it was freed (a dangling pointer), infinite or very deep recursion that overflows the stack, and writing to read-only memory such as a string literal. In managed languages a segfault usually points at a bug in a native extension.
