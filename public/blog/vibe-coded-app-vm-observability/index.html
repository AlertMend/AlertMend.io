Vibe-Coded App: What About Observability?

A
AlertMend Team
2026-06-20

Read this before you close the terminal

You deployed your app. You did not deploy observability.

Cursor, Bolt, Replit, and Lovable optimize for shipping. They do not leave you with uptime checks, log access, disk alerts, or anyone to page when production breaks. The server looks fine. Your users may not.

Tonight, 3am

Your app died hours ago. You do not know yet.

The server still accepts SSH. The cloud console looks green. Nobody was paged. You find out from a user DM at breakfast.

Right before a demo

The site shows 502. You cannot see why.

nginx is running. Your app process is not. You tested localhost yesterday and assumed production was the same.

Week two on a $12 server

Disk fills. The app starts failing writes.

Logs and Docker layers grow quietly. No alert fired because nobody watched disk. A restart does not fix a full disk.

The silent hang

The process exists. Requests stop working.

PID is there. CPU looks idle. Users time out and leave. You only notice when signup emails stop.

Deploy is not the finish line. Without observability, your first production incident is not a question of if. It is a question of whether you find out before or after your users do.

The fix (minimum viable observability)

Good news: You do not need Kubernetes or a metrics stack on day one. You need four things: an uptime check, disk and memory awareness, logs you can read in one command, and one alert channel when something fails twice.

The lie you are living with right now

Most vibe-coded deploys end with: URL loads in browser, screenshot for Twitter, close laptop. That proves the app worked once, at one moment, from your machine.

It does not prove the process will stay up, that disk will not fill, that nginx can reach the app tomorrow, or that anyone will tell you when signup stops working. Refreshing the URL is not observability.

What vibe coding usually skips

Process dies overnight

The app exits after a deploy or memory spike. The server still accepts SSH.

Fix: Add a restart policy (systemd, Docker, PM2) plus an external uptime check.

Disk fills silently

Logs and Docker layers grow until writes fail and the app crashes.

Fix: Alert when disk use crosses 85%. Rotate logs with logrotate.

Memory leak

The app slows down over days. You only notice when users complain.

Fix: Watch process memory with pm2 monit or host-level metrics.

Bad deploy

You pushed a broken build. No rollback signal, no alert.

Fix: Health check after deploy; keep the last working release one command away.

There are only a few ways you actually get deployed

We have wired observability on production apps from solo founders to teams running AI services on cloud servers. Every vibe-coded stack looks different in the repo. Once you are on a real server, you almost always land in one of three deployment patterns. The AI tool that generated your code does not change that.

How you are deployedTypical vibe-coded stackWhat to check first
systemd servicePython FastAPI, Node API, Go binary on Ubuntusystemctl status · journalctl -u
Docker / ComposeAI-generated Dockerfile on a DigitalOcean or AWS serverdocker ps · docker logs · healthcheck
PM2 processNode / Next.js API running directly on the hostpm2 list · pm2 logs · pm2 monit

nginx or Caddy in front of the app is common across all three. That is why you can see 502 Bad Gateway while SSH still works: the proxy is up, your app process is not. Pick your pattern below. The observability basics stay the same.

Day 1 setup: pick your deployment pattern

Choose the one that matches how your app actually runs in production.

Day 1: systemd service

    Four steps to add observability today

    1

    Add a health endpoint

    Return 200 from GET /health with a cheap DB or cache ping if you have one.

    2

    Pick one log command

    journalctl -u app, docker logs -f, or pm2 logs, and save it in your runbook.

    3

    Schedule two checks

    External uptime ping plus a weekly df -h / free -h reminder on the server.

    4

    Wire one alert channel

    Slack webhook or email when the uptime check fails. That is enough for day one.

    What to alert on first

    SignalWhenAction
    Site downHTTP check fails twice in a rowPage on-call or yourself in Slack
    Disk above 85%df on the server crosses thresholdClean logs/images before the disk is full
    Process not runningsystemctl inactive or container exitedAuto-restart plus alert if it keeps failing
    High memoryApp or server memory sustained above 90%Restart or resize before OOM kills the process
