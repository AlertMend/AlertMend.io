The 30-second answer

Code 1 is not the diagnosis. The line above it is.

QEMU exited with code 1 means the VM start process failed, but the real cause is usually one line earlier in the Proxmox task log: image lock, storage unavailable, bad config, KVM unavailable, passthrough conflict, or disk image damage.

What “start failed: QEMU exited with code 1” means

In Proxmox, the web UI often shows a short wrapper error. The useful diagnosis is the first specific message from QEMU, storage, KVM, VFIO, or the host kernel. Treat code 1 as the smoke alarm, not the fire.

Rule: copy the full task log before changing anything. If you only have “QEMU exited with code 1,” you do not yet have the cause.

Most common

Image lock or stale process: “Is another process using the image?”

Most operational

Storage unavailable: full disk, offline NFS/iSCSI, unhealthy Ceph, or ZFS issue.

Most dangerous

Disk image repair: only check or repair when the image is not in use.

Pick the real error

Same code 1. Different fix.

Select the clue from your task log. The generic code is the same, but the safe action changes completely.

$ observed task log TASK ERROR: start failed: QEMU exited with code 1 qemu: Failed to get "write" lock Is another process using the image?
Interpretation

The disk image is already open or still locked by another process.

This usually happens after a stuck backup, migration, previous QEMU process, storage hiccup, or duplicate start. Do not repair the disk while something may still hold it.

qm status 101
qm config 101
ps -ef | grep "[q]emu-system.*101"
lsof | grep "vm-101-disk"

Fix: Confirm no backup, migration, or QEMU process is active. Only then clear stale Proxmox locks or stop the stale process through the safest control path.

Safe fix checklist

Run these checks in order. The goal is to avoid fixing the wrong layer under pressure.

1

Save the task log

Copy the full Proxmox task output. The exact line above code 1 determines the fix.

2

Check VM state

Run qm status <vmid>, inspect active jobs, and confirm this is not a backup, migration, or duplicate start.

3

Check storage

Run pvesm status, df -h, and the storage-specific health command for ZFS, Ceph, NFS, or iSCSI.

4

Check config and host

Run qm config <vmid>, then check KVM modules, bridges, passthrough devices, and disk paths.

If the log says “is another process using the image”

This query showed up directly in Search Console, and it deserves a careful answer. Image-lock errors are where people most often make the situation worse by unlocking too early or running repair commands on an active disk.

  • Check the VM: qm status <vmid> should not report a running VM unless you are debugging a duplicate start.
  • Check Proxmox tasks: look for backup, snapshot, migration, replication, or restore work involving the same VM or storage.
  • Check QEMU processes: confirm no stale qemu-system process still references the VM ID or disk path.
  • Check disk owners: use lsof or storage-specific tooling to identify who has the disk open.
  • Only then unlock: use qm unlock <vmid> only after proving the lock is stale, not active protection.
Important: QEMU’s own disk-image documentation warns not to modify images that are in use. That includes repair workflows. If the image may still be owned by a process, stop there and identify the owner first.

What not to do first

Avoid the panic fix

qm unlock + kill -9 + repair

Those commands may be valid in narrow cases, but they are not the first move. If a backup, migration, storage operation, or QEMU process is still legitimately using the image, forcing your way past the lock can risk data integrity.

How you can automate QEMU code 1 diagnosis

This class of incident is perfect for automation because the useful evidence is structured: VM ID, Proxmox task log, VM config, storage status, running QEMU processes, host kernel logs, passthrough device state, and recent backup/migration jobs.
