How do I monitor data quality in Oracle?

Many banks, insurers and large enterprises still run core reporting on Oracle, usually loaded overnight by Oracle Data Integrator (ODI). Monitoring data quality there matters as much as in a cloud warehouse, and the mechanics are the same: express each rule as a query, run it on a schedule, and alert when the result crosses a threshold.

The difference on Oracle is the database itself. It often serves operational traffic alongside your reporting tables, so checks have to be light and read-only. And the SQL has Oracle quirks that will silently break a check written for another engine: SYSDATE for the current time, an empty string that Oracle stores as NULL, and FETCH FIRST rather than LIMIT.

  • Start with the four checks that catch most incidents: completeness, uniqueness, validity and freshness.
  • Add referential integrity where foreign keys matter, such as loans that must resolve to an account.
  • Run everything as a read-only user with a query-time cap so a check never competes with a production load.
  • Link each monitored table to the ODI job that loads it, so a failure names its cause instead of just a dropped row count.

Core checks in Oracle SQL

Every query below is aggregate-only and returns a single count or number, so it is cheap to run and easy to threshold. Use sample names such as BANKING.CUSTOMER_ACCOUNTS and swap in your own.

Completeness checks that mandatory columns are filled. In Oracle an empty string is stored as NULL, so TRIM(address) IS NULL catches both true nulls and whitespace-only values in one condition.

Uniqueness checks that a key has no duplicates. FETCH FIRST caps the rows returned so the check stays light even when a bad load creates many duplicates.

Validity checks that values sit in the allowed set or range. Combine set membership and a numeric range in one pass.

Freshness checks that today's data arrived. SYSDATE minus the newest load timestamp is a fraction of a day, so multiply by 24 and 60 to read the gap in minutes.

Referential integrity checks that foreign keys resolve. NOT EXISTS reads well and lets Oracle use an index on the parent key.

In practice: A nightly ODI load fails, and the report is fixed before the 9am meeting

At 06:12 the ODI job nightly_load stops with ORA-01400 (cannot insert NULL) while loading BANKING.CUSTOMER_ACCOUNTS.

The uniqueness check on account_id fails at 98.7 percent, and the completeness check on customer_id drops below its threshold.

The alert to Teams names nightly_load and the ORA-01400 error as the cause, and lists the three Power BI reports that read the table as the impact.

A red number tells you something broke. Naming the ODI job and the affected reports tells the on-call analyst what to fix and who to warn, before a business user opens the wrong dashboard.

How do I keep checks light on a production database?

Oracle frequently serves operational workloads alongside reporting, so a heavy check run at the wrong moment can slow the whole database. The goal is checks that are invisible to production.

  1. Use a read-only user
    Give the checking account only SELECT on the tables it reads. A generated least-privilege grant script keeps the role tight and auditable.
  2. Cap query time
    Set a resource limit or statement timeout so a runaway check is killed rather than left to contend with a load.
  3. Schedule after loads, not during peak
    Run heavy checks right after nightly_load completes, and keep only cheap freshness checks in business hours.
  4. Prefer aggregates and samples
    Return counts and a capped sample of offending rows with FETCH FIRST, never a full-table export.
Watch the anomaly and trend checks

History-based checks like anomaly z-score and trend are useful but read more data. Run them off-peak, and without enough history a check should wait rather than guess.

Linking failures to Oracle ODI jobs

When a check fails, the fastest explanation is usually the load job. An ODI session that failed or partially loaded, for example on a constraint error such as ORA-01400 (cannot insert NULL), explains most completeness and volume failures.

Linking each monitored table to the ODI job that loads it turns the alert from 'row count dropped' into 'nightly_load failed with ORA-01400'. That is the cause. Pair it with the downstream reports that read the table, and you also have the impact, so the on-call analyst knows what to fix and who to warn in the same alert.

  • Cause: the ODI session name, its status, and the ORA- error it stopped on.
  • Impact: the Power BI reports that read the affected table, flagged before anyone opens them.
  • Both stitched onto the failed check and sent to Slack or Teams with the policy clause the check enforces.
