What keeps Mattermost and Rocket.Chat up

Mattermost and Rocket.Chat are self-hosted team chat platforms where the value is real-time messaging, and that depends on a websocket and a healthy database. Mattermost runs a Go server on PostgreSQL, and Rocket.Chat runs a Node server on MongoDB and needs a replica set with a working oplog for live updates.

A page that loads over HTTP is not proof that messages are flowing, because the websocket upgrade can fail at the proxy while login still works. Monitoring team chat means watching the websocket, the app process, and the database together.

App process and memory

PostgreSQL for Mattermost; MongoDB replica set health and oplog for Rocket.Chat, required for real-time updates.

Copy-paste health checks

Both apps expose a health or ping endpoint; pair it with a database and websocket check.

# Mattermost system ping (returns status)
curl -s https://your-mattermost/api/v4/system/ping

# Rocket.Chat basic info / health
curl -s https://your-rocketchat/api/info

# Rocket.Chat MongoDB replica set (oplog needed for real-time)
mongosh --quiet --eval "rs.status().ok"

# Mattermost PostgreSQL reachable
pg_isready -h 127.0.0.1 -p 5432

# Confirm the websocket upgrade is proxied (expect HTTP 101)
curl -sI -o /dev/null -w "%{http_code}" -H "Connection: Upgrade" -H "Upgrade: websocket" https://your-chat/

Monitor Mattermost and Rocket.Chat with Prometheus and Grafana

Both platforms expose Prometheus metrics natively. In Mattermost (Enterprise), enable Performance Monitoring in the System Console and set a listen address such as port 8067; it exposes mattermost_api_time plus cache, cluster, and login metrics with Mattermost-provided Grafana dashboards. Rocket.Chat exposes metrics on port 9458 when enabled, including Node.js event-loop lag, heap and GC, messages, oplog activity, and push-queue size.

# Rocket.Chat metrics (enable in Admin, then scrape port 9458)
curl -s http://your-rocketchat:9458/metrics | head

# Mattermost metrics (Enterprise; set the listen address in the System Console)
curl -s http://your-mattermost:8067/metrics | head

Key metrics to scrape and graph in Grafana:

  • Node.js event-loop lag, heap, and GC (Rocket.Chat)
  • mattermost_api_time and cluster metrics (Mattermost)
  • messages sent and websocket or DDP sessions
  • oplog activity and push-queue size

Common failures and safe fixes

Websocket not connecting

Login works but messages do not appear live because the reverse proxy is not forwarding the websocket upgrade to the chat port.

Fix: Add the Upgrade and Connection headers and correct port to the proxy config, then confirm a 101 response and live message delivery.

Rocket.Chat high memory or CPU

The Node process climbs in memory or CPU, often from MongoDB oplog issues, large rooms, or a bad integration.

Fix: Check the MongoDB replica set and oplog, restart the instance to reclaim memory, and scale to multiple instances behind the proxy.

MongoDB replica or oplog issues

Rocket.Chat needs a replica set with a working oplog for real-time updates; a standalone or lagging Mongo breaks live messaging.

Fix: Run MongoDB as a replica set, watch replication lag and oplog window, and restore a healthy secondary before it stalls updates.

Mattermost 500 or crash

A bad config, failed migration, or PostgreSQL problem takes the Mattermost process down or into an error loop.

Fix: Read the server log, verify PostgreSQL and the config, restart the service, and verify the ping endpoint and a test login.

Push notifications failing

Mobile users stop getting notified when the push proxy or gateway certificate or connectivity fails.

Fix: Check the push proxy status and certificates, confirm outbound connectivity, and alert on push delivery failures.
