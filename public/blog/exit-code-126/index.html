The 10-second answer

Exit code 126 means: found, but not executable.

If you see exit code 126, the shell or runtime usually found the command path, but could not invoke it. Start with the command immediately above the error, then check permissions, file type, shebang, mount options, and runtime architecture.

What exit code 126 means in Bash and Linux

For a developer or SRE, the practical meaning is: the command exists, but the runtime could not execute it. Bash documents command lookup and execution separately: if a command is not found, Bash returns 127; if it is found but execution cannot proceed, you should investigate invocation problems rather than installation alone.

TL;DR: Do not reinstall everything. First prove whether the target is executable by the same user, on the same filesystem, inside the same container or CI runner.
StatusPlain EnglishTypical messageFirst fix
126 Found, but cannot execute. Permission denied, is a directory, bad interpreter, exec format error Inspect mode, shebang, mount options, file type, and architecture.
127 Command not found. command not found, not found or does not exist Fix PATH, install the tool, or correct command spelling.
125 Docker itself failed before the container command ran. Bad Docker flag, daemon/runtime issue. Fix the Docker invocation or daemon problem.

No log upload
$ ./script.sh bash: ./script.sh: Permission denied $ echo $? 126
Interpretation

The file is present, but not executable by this user.

Check the execute bit and parent directory access. Prefer a narrow permission change over chmod 777.

ls -l ./script.sh chmod u+x ./script.sh ./script.sh

Fix: add execute permission for the intended owner/group, or run it with an interpreter when that is the right contract: bash ./script.sh.

$ docker run busybox /etc Container command '/etc' could not be invoked. 126
Interpretation

Docker could not invoke the contained command.

The command may be a directory, a script without execute permission, a broken entrypoint, or a binary built for another architecture.

docker image inspect IMAGE --format '{{json .Config.Entrypoint}} {{json .Config.Cmd}}' docker run --rm --entrypoint sh IMAGE -lc 'ls -l /app && file /app/start'

Fix: correct ENTRYPOINT/CMD, add execute permission during build, or rebuild for the target platform.

Run npm run build sh: ./scripts/build.sh: Permission denied Error: Process completed with exit code 126.
Interpretation

The runner is reporting the child process status.

Local permission changes do not always survive Git. Store the executable bit in the repository when a CI runner must execute a script directly.

git update-index --chmod=+x scripts/build.sh git commit -m "Mark build script executable"

Fix: preserve executable mode in Git, or call the script through an explicit interpreter in package.json or the workflow.

$ kubectl logs app-7f9c exec /app/start: permission denied $ kubectl get pod app-7f9c CrashLoopBackOff
Interpretation

The container starts, then the entry command cannot run.

Look at the image entrypoint, mounted volumes, security context, and platform. A ConfigMap-mounted script may not behave like a file baked into the image.

kubectl describe pod POD kubectl logs POD --previous kubectl get pod POD -o jsonpath='{.spec.containers[0].command}'

Fix: adjust image permissions, command/args, volume mount strategy, or image architecture, then redeploy safely.

How to fix exit code 126 safely

The fastest path is not “try chmod and hope.” Run the diagnosis in the same place the process failed: same user, same container, same CI runner, same filesystem.

1

Find the producer

Read the command immediately before exit code 126. CI, npm, systemd, or Kubernetes may only be reporting a child process result.

2

Check the target

Run ls -ld and file. You need to know whether it is a script, binary, symlink, directory, or wrong-platform executable.

3

Validate the interpreter

Read the shebang. Confirm /bin/bash, /usr/bin/env, Python, Node, or sh exists in that runtime image or host.

4

Fix the real blocker

Apply the smallest safe change: executable bit, Git mode, Docker command, CRLF cleanup, noexec mount policy, or architecture rebuild.

Docker, npm, and CI: where 126 gets confusing

You may see the same failure phrased as command terminated with exit code 126, npm error code 126, or process completed with exit code 126. Those wrappers usually do not define the number; they report the program or container command that failed underneath.

Docker: If Docker returns 126, inspect ENTRYPOINT, CMD, file mode, image platform, and whether a mounted file replaced an executable from the image.
npm: npm often reports the exit code of the script command. Look inside package.json, then inspect the script file or binary that line invokes.
GitHub Actions / CI: the runner message is a wrapper. Store executable mode in Git, avoid relying on a local-only chmod, and print ls -l during diagnosis.

Kubernetes exit code 126 and CrashLoopBackOff

In Kubernetes, you may not see “exit code 126” first. You may see CrashLoopBackOff, then logs like exec /app/start: permission denied. The fix is still the same investigation, but you need to look through the pod specification and image, not only the shell.

1

Read previous logs

kubectl logs POD --previous often contains the real execution error from the failed container start.

2

Inspect command and args

Compare the pod command/args with the image entrypoint and the file that actually exists in the container.

3

Check mounts and security context

Mounted config, secret, or volume content may not have the same mode as files baked into the image.

4

Verify platform

Confirm the image architecture matches the node architecture, especially on mixed arm64/amd64 clusters.

Exit code 126 FAQ

In Bash-style shells, exit code 126 usually means the command was found but could not be executed. Common causes include missing execute permission, trying to execute a directory, a bad shebang, a noexec mount, or a binary built for the wrong OS or CPU architecture.
