What to watch

The Collector failure signals that actually matter

The OpenTelemetry Collector has receivers, processors, exporters, connectors, and extensions. Monitoring only the process misses the point. You need to know whether telemetry is entering, moving through, and leaving the pipeline.

Health

Use the health_check extension for process-level health. Treat it as necessary, not sufficient.

health_check: 0.0.0.0:13133

Receiver intake

Watch accepted and refused telemetry by signal type. Refused items mean clients are losing data or retrying.

otelcol_receiver_refused_spans

Exporter delivery

Exporter send failures mean the Collector got data but could not deliver it to the destination.

otelcol_exporter_send_failed_spans

Queue pressure

Queue size near capacity is the early warning. Failed enqueue is the loss signal.

otelcol_exporter_queue_size

Memory and heap

RSS and heap growth often predict OOMKilled restarts before Kubernetes tells you it happened.

otelcol_process_memory_rss

Runtime context

Pod restarts, OOMKilled, rollouts, resource limits, network policy, and backend DNS make the metrics actionable.

kubectl describe pod
Version note: Collector metric names can vary by version and Prometheus export settings. Always verify the exact names in your own /metrics output before writing alerts.

Symptom decoder: what the Collector is trying to tell you

Engineers usually land on this problem through a symptom, not a metric name. Use this decoder when traces disappear, exporter errors spike, queues fill, or Collector pods keep restarting.

otelcol is running
backend shows no new traces
receiver accepted count is flat
Interpretation

The process is alive, but data is not entering the active pipeline or is being exported to the wrong destination.

  • Confirm the app exports to the right OTLP endpoint and protocol.
  • Verify the receiver appears in service.pipelines.
  • Check Collector logs for connection, TLS, or auth errors.

Safe fix: Fix endpoint or pipeline wiring first. Do not restart the application until you prove the Collector is actually receiving data.

exporter send failed spans increasing
retry backoff in collector logs
backend ingest errors
Interpretation

The Collector is receiving data but cannot deliver it to the backend. This is often auth, DNS, network, TLS, backend throttling, or exporter config.

  • Test backend DNS and network egress from the Collector pod or VM.
  • Validate credentials, headers, TLS settings, and endpoint path.
  • Look for backend rate limits or ingest quota failures.

Safe fix: Repair the exporter destination, then watch queue size drain. If the queue keeps growing, scale the gateway or fail over to a secondary export path.

exporter queue size near capacity
enqueue failed metrics increasing
telemetry lag rising
Interpretation

The backend is slow or the Collector is underprovisioned. Once enqueue failures begin, telemetry is being lost.

  • Compare queue size with queue capacity.
  • Check CPU, memory, and exporter in-flight requests.
  • Look for backend latency or throttling.

Safe fix: Scale gateways, increase safe queue capacity, tune batch settings, reduce burst volume, or route critical telemetry through a separate pipeline.

pod restarted
last state OOMKilled
memory rss climbs before crash
Interpretation

The Collector is running out of memory or receiving a burst it cannot buffer. A simple restart may only reset the clock.

  • Check memory limiter configuration.
  • Inspect queue size, batch sizes, and cardinality-heavy metrics.
  • Review resource requests, limits, and node pressure.

Safe fix: Add or tune memory_limiter, right-size pod limits, scale the Collector layer, and reduce high-cardinality or low-value telemetry before export.

receiver refused spans increasing
accepted items still increasing
client retry errors
Interpretation

The receiver is rejecting some telemetry. Causes include malformed payloads, unsupported protocol, backpressure, or pipeline overload.

  • Check receiver protocol and payload format.
  • Compare refused counts by signal type.
  • Look for overloaded processors or exporters downstream.

Safe fix: Fix client export settings or reduce pressure downstream. If refused counts spike during deploys, correlate with new instrumentation or traffic shape.

Copy-paste starter config for Collector self-monitoring

Use this as a starter pattern, then adapt it to your Collector distribution, version, security policy, and backend. The important part is exposing health and internal metrics, then enabling the extensions in the service section.

otel-collector-self-monitoring.yaml 
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  memory_limiter:
    check_interval: 5s
    limit_percentage: 80
    spike_limit_percentage: 20
  batch:
    timeout: 5s
    send_batch_size: 8192

exporters:
  otlp/primary:
    endpoint: observability-backend.example.com:4317
    sending_queue:
      enabled: true
      queue_size: 10000
    retry_on_failure:
      enabled: true
      initial_interval: 5s
      max_interval: 30s
      max_elapsed_time: 300s

extensions:
  health_check:
    endpoint: 0.0.0.0:13133
  pprof:
    endpoint: 0.0.0.0:1777
  zpages:
    endpoint: 0.0.0.0:55679

service:
  extensions: [health_check, pprof, zpages]
  telemetry:
    metrics:
      readers:
        - pull:
            exporter:
              prometheus:
                host: 0.0.0.0
                port: 8888
                without_type_suffix: true
                without_units: true
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp/primary]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp/primary]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp/primary]
Expose carefullyKeep pprof and zPages restricted. They are diagnostic endpoints, not public endpoints.
Scrape internal metricsPort 8888 is where the Collector commonly exposes its own Prometheus metrics.
Use memory_limiterIt is one of the guardrails that prevents telemetry bursts from taking the Collector down.

Alert rules that are worth waking someone for

Do not wake people for every small movement. Wake them when the telemetry pipeline is losing data, close to losing data, or making the rest of observability untrustworthy.

Signal Why it matters First check Safe action
Exporter send failures increasing Data is received but not delivered. Backend endpoint, auth, TLS, DNS, network policy. Repair exporter path, fail over, or pause risky rollout.
Queue utilization above 80% The backend is slow or the Collector is overloaded. Queue capacity, backend latency, CPU, memory. Scale gateway, tune batch, reduce burst, or route critical telemetry.
Failed enqueue above zero The Collector is dropping telemetry. Queue full, retry pressure, backend throttling. Escalate immediately and preserve evidence.
Receiver refused items increasing Clients may be rejected or misconfigured. Protocol, endpoint, payload format, downstream pressure. Fix client export config or relieve pipeline pressure.
Memory RSS near limit OOM restarts can silently create telemetry gaps. memory_limiter, queue size, batch size, cardinality. Scale, tune memory limiter, reduce high-cardinality data.

Kubernetes checklist for OpenTelemetry Collector monitoring

In Kubernetes, Collector failures often look like generic platform problems until you connect the dots. Add these checks so the responder can move from symptom to fix quickly.

DaemonSet or gateway?

Know whether the Collector runs on every node, centrally as a Deployment, or both.

Requests and limits

Right-size CPU and memory. Avoid tiny limits that create OOMKilled loops during traffic bursts.

Probes

Use health_check for liveness/readiness, but pair it with pipeline metrics.

Rollout history

Correlate failures with config maps, Collector image changes, operator changes, or backend migration.

Network and secrets

Check egress policy, service DNS, exporter auth headers, TLS certs, and secret rotation.

Scrape target

Make sure Prometheus or your scraper can reach the internal metrics endpoint.

Common mistakes that make Collector incidents worse

Only checking pod health

A healthy pod can still drop spans, fail exports, or build a queue that is about to overflow.

Configuring a receiver but not enabling the pipeline

In Collector config, a component is not active until the service pipeline uses it.

No queue alerts

Queue pressure is the early warning. Failed enqueue means you are already losing data.

No memory limiter

Telemetry bursts can turn into OOMKilled loops if the Collector is allowed to grow until Kubernetes kills it.

Ignoring the backend

Exporter failures are often caused by the destination, not by the Collector process itself.

No owner or runbook

Alerting on Collector failures without an owner, runbook, and rollback path still leaves teams guessing.

How you can automate the boring recovery path

Once the checks are reliable, many Collector incidents should not stay manual. The key is to automate only actions that are safe, observable, and reversible.

DetectQueue, refused items, exporter failures, restarts, memory, backend errors.
→
CorrelateConfig change, rollout, network policy, credentials, backend throttling, node pressure.
→
DecideRestart, scale, rollback, fail over, or ask for approval.
→
VerifyQueue drains, exports recover, refused items stop, backend data resumes.
