THE 10-SECOND ANSWERSlow search usually means the right cache is not being used, not that caching is broken.

The three Elasticsearch caches

The node query cache stores eligible filter results per node. The shard request cache stores a shard’s response and, by default, caches requests with size: 0; setting request_cache=true can opt other requests in when they are otherwise cacheable. Fielddata is different: it loads values for text sorting and aggregation on the JVM heap.

A low hit rate is usually not a broken cache. The query may be ineligible, may contain unrounded nowmay change its JSON body between requests, or the cache may be evicting before reuse. The fix is to prove eligibility and reuse first, then size a cache only if the working set justifies the memory.

How to diagnose it

1

Read cache stats

Run GET _nodes/stats/indices/query_cache,request_cache,fielddata. For each cache compare hit_count to miss_count and watch evictions; high evictions mean the cache is too small or churning.

2

Check whether the query is cacheable

By default, the shard request cache caches size: 0 requests. request_cache=true can opt in other eligible requests, but non-deterministic queries such as unrounded now still miss.

3

Look at fielddata memory

Run GET _cat/fielddata?v&s=size:desc. Large fielddata is text sorting or aggregation loading into heap; that is a mapping problem, not a caching benefit.

4

Compare per node

Run GET _cat/nodes?v&h=name,qcm,rcm,fm to see query-cache, request-cache, and fielddata memory per node and spot an imbalanced or saturated node.

Common causes and fixes

Query is not cacheable

The request uses unrounded now, a changing body, or the default path with size greater than zero.

Fix: Use size: 0 for aggregation-only dashboards, round date math, and canonicalize request JSON so identical work produces an identical cache key.

Cache too small, high evictions

The request or query cache evicts entries before they are reused.

Fix: Prove reuse first. Then adjust the relevant static node cache setting conservatively, restart as required, and re-measure heap and latency.

Fielddata mistaken for a cache win

Text aggregations load fielddata into heap; this is not a response-cache hit.

Fix: Aggregate on keyword sub-fields with disk-backed doc values instead of enabling fielddata on text.

Constant writes invalidate caches

Frequent refreshes on an index clear its cached results every interval.

Fix: Increase index.refresh_interval on high-ingest indices so cached aggregations survive longer.

Request cache disabled

The index or request has request caching turned off.

Fix: Enable index.requests.cache.enable or pass request_cache=true on the search.

Fix it step by step

Make the query cacheable, size the cache to fit the working set, and slow the refresh on read-heavy indices so caches survive.

# 1. Make a dashboard aggregation cacheable: size:0 + rounded date math
GET /metrics-*/_search?request_cache=true
{
  "size": 0,
  "query": { "range": { "@timestamp": { "gte": "now-24h/h" } } },
  "aggs": { "per_hour": { "date_histogram": { "field": "@timestamp", "calendar_interval": "hour" } } }
}

# 2. Give read-heavy indices a longer refresh so caches are not wiped each second
PUT /metrics-*/_settings
{ "index.refresh_interval": "30s" }

# 3. Size the request cache (default is ~1% of heap)
# elasticsearch.yml:
indices.requests.cache.size: 2%

The single biggest win is often date rounding: now-24h/h resolves consistently within the hour, so identical dashboard requests can reuse the same cache entry. Cache-size settings are static node settings; change them only after proving eviction is the bottleneck.

Prevent slow-cache problems

Design for the read pattern. Aggregation-only dashboards should normally use size:0 with rounded date math, and mappings should send sorting and aggregation to keyword fields with disk-backed doc values rather than text fielddata.

# mapping: keep a keyword sub-field for aggregations and sorting
"properties": {
  "status": {
    "type": "text",
    "fields": { "keyword": { "type": "keyword" } }
  }
}

On high-ingest indices, relax index.refresh_interval so cached results are not invalidated every second, and monitor cache hit rate and evictions so you tune sizing before users feel the slowdown.
