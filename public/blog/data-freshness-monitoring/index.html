What is data freshness monitoring?

Freshness is the single most common data quality problem and the easiest to miss, because nothing fails loudly. No job errors, no page fills with red. The report loads, the totals look reasonable, and they are a day old.

Data freshness monitoring answers one question for every important table: did the data we expected arrive in time for the reports that depend on it? It is a yes or no question, checked continuously, against an expectation you set per table.

This post is a single pillar deep dive on freshness alone. For the other nine check families in the catalog, completeness, uniqueness, validity, format, referential integrity, numeric range, volume, anomaly and trend, see the /blog/data-quality-check-types hub.

Freshness is measured against an expectation, not a clock

A table is not late because it is 08:00 and it has not loaded. It is late because it was expected by 06:30 and it is now past your tolerance. Expected arrival time, not a fixed wall clock, is what makes a freshness signal trustworthy.

How do you define a freshness SLA per table?

A freshness signal is only meaningful against an agreed expectation. One blanket rule for the whole warehouse produces noise on hourly tables and misses slow daily ones. Define the SLA per table, and tie it to the reporting deadline it feeds.

  1. Set the expected arrival time
    For example, loaded by 06:30 on business days. Anchor it to the deadline of the report that reads the table, not to when the job usually happens to finish.
  2. Name the update pattern
    Daily batch, hourly micro batch or continuous stream. This decides whether you measure lateness in hours or minutes.
  3. Set a tolerance
    How far past the expected arrival counts as late. A 30 minute grace on a 06:30 deadline is common for a nightly load.
  4. Assign an owner
    The person or channel that is alerted, so a late table has a name attached before anyone asks whose it is.
In practice: A late nightly load, caught before the 9am review

At 06:12 the freshness check on BANKING.LOANS_DAILY_BALANCE sees the latest business date is still yesterday, past the 06:30 expected arrival with a 30 minute tolerance.

The check is linked to the Oracle ODI job nightly_load, which stopped on an error, so the alert names the job and the error instead of only saying the table is late.

Three Power BI reports read this table, so their owners get a heads up in Microsoft Teams before the 9am balance review opens a stale dashboard.

A freshness alert that names the stalled job and the affected reports turns a two hour investigation into a five minute fix, because nobody has to guess what broke or who to warn.

How do you measure freshness in Snowflake?

The most reliable signal is a load timestamp written by the pipeline. The simplest form measures how long it has been since the table last loaded.

Minutes since load is a fixed clock signal. It cannot tell you whether the table is actually late for today, because 200 minutes since load is fine at 07:00 and a problem at 06:20. To judge lateness you compare against the expected arrival time for the current date, and you also check the latest business date in the data, because a job can touch a table without adding a new day.

No load timestamp? Prefer the business date

If a table has no loaded_at column, use the latest business date in the data, such as MAX(balance_date), rather than the warehouse last-modified metadata. A table can be modified by a job that wrote nothing new, so last-modified time can read fresh while the data is stale.

Why is freshness not the same as volume?

A job can finish on time and load too little. Freshness says the data arrived. Volume says enough of it arrived. They are different failures, and a freshness check alone will pass while a half-empty table quietly feeds every report downstream.

Pair each freshness check with a volume check that compares today rows against recent history. Together they catch the two most common load failures: nothing arrived, or not enough arrived.

How do you trace late data back to the pipeline job?

A freshness alert that only says table is 3 hours late starts an investigation. A useful alert also says why, by naming the job that loads the table and its state.

Linking each freshness check to the pipeline job that populates its table turns a late-data alert into a cause you can act on. The three usual causes are:

  • the Airflow task that loads the table is stuck in retry,
  • the Oracle ODI job failed with a specific error, or
  • an upstream source did not deliver on time.

The other half of a good alert is impact: the reports and dashboards that read the late table. The goal is to warn report owners before business users open a stale report and start asking why the numbers moved. For the mechanics of report-level impact, see /blog/power-bi-data-quality-impact-analysis.

Keep freshness checks quiet around known gaps

Freshness checks get noisy around weekends, holidays and planned maintenance. Use business-day calendars, maintenance windows that pause checks, cooldowns so one late table does not page repeatedly, and flapping detection for tables that hover around the threshold.
