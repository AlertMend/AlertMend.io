Why the heap fills up

Elasticsearch runs on the JVM, and every shard, mapping, cache, and in-flight request consumes heap. Two forces push it up: sizing (too little heap, or paradoxically too much) and demand (fielddata on text fields, large aggregations, and the fixed per-shard overhead of running thousands of shards).

When heap stays high the garbage collector runs longer and more often, adding latency, and circuit breakers start rejecting requests to avoid an OutOfMemory crash. High heap is therefore both a symptom and a cause: fix the sizing, then remove the demand that keeps refilling it.

# GET _cat/nodes?v&h=name,heap.percent,ram.percent
# name    heap.percent ram.percent
# es-data-0   92          88

How to diagnose it

1

Calculate old-gen pressure

Run GET _nodes/stats?filter_path=nodes.*.jvm.mem.pools.old and calculate used_in_bytes / max_in_bytes. Sustained pressure above 85% needs action; a brief sawtooth spike may be normal.

2

Check circuit breakers

Run GET _nodes/stats/breaker. The parentfielddataand request breakers show what is tripping and how close each is to its limit.

3

Find fielddata hogs

Run GET _cat/fielddata?v&s=size:desc. Large fielddata usually means aggregating or sorting on a text field, which loads the whole field into heap.

4

Count your shards

Run GET _cat/shards?v | wc -l style checks or GET _cluster/health. Thousands of tiny shards carry fixed heap overhead; Elastic recommends keeping shards in the tens of GB, not hundreds of MB.

Common causes and fixes

Manual heap override is wrong

A custom Xms/Xmx ignores node roles or consumes memory needed by the filesystem cache.

Fix: Return to automatic heap sizing where possible. If you must override, keep Xms equal to Xmx and no more than 50% of memory available to the node or container.

Fielddata on text fields

Aggregating or sorting on a text field loads every term into heap.

Fix: Use a keyword sub-field with doc_values for aggregations and sorting instead of enabling fielddata.

Too many shards

Thousands of small shards multiply per-shard heap overhead.

Fix: Consolidate with ILM rollover and shrink; target shards in the tens of GB.

Expensive aggregations

High-cardinality terms aggregations or deep nested aggs build large in-heap structures.

Fix: Add search.max_buckets limits, use composite aggregations, and cap cardinality.

Mapping explosion

Dynamic mapping creates thousands of fields, each with overhead.

Fix: Disable or constrain dynamic mapping and set index.mapping.total_fields.limit deliberately.

Fix it step by step

Identify the consumer before changing capacity. Correct query and mapping demand first; revisit heap sizing only when the measured workload still exceeds the node.

# 1. Measure old-generation memory pressure
GET _nodes/stats?filter_path=nodes.*.name,nodes.*.jvm.mem.pools.old

# 2. Stop aggregating on text; use the keyword sub-field
GET /my-index/_search
{
  "size": 0,
  "aggs": { "by_status": { "terms": { "field": "status.keyword" } } }
}

# 3. Bound runaway aggregations
PUT _cluster/settings
{ "persistent": { "search.max_buckets": 20000 } }

# 4. Temporary relief only after confirming fielddata is the consumer
POST /my-index/_cache/clear?fielddata=true

Clearing the fielddata cache frees heap immediately but it refills on the next text aggregation. The lasting fix is mapping (keyword + doc_values) and shard count, not repeated cache clears.

Prevent heap pressure

Prefer Elasticsearch automatic heap sizing, which considers node roles and available memory. If a measured workload requires a manual override, use a custom JVM options file, keep Xms equal to Xmx, and allocate no more than 50% of memory available to the node or container.

# Example custom JVM options file for a measured 16Gi container
# config/jvm.options.d/heap.options
-Xms8g
-Xmx8g

# Keep the remaining memory available for the OS and filesystem cache.

Design mappings so aggregations and sorts hit keyword fields with doc_values, use ILM to keep shard counts sane, and alert on heap crossing 80% so you tune before the circuit breakers trip.
